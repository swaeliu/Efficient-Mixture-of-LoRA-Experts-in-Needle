# Phase 4 summary — robustness, implicit regimes, transformer integration

Date: 2026-11-08. Branch `main`. All measurements are CPU-only (hw2 Needle,
NumPy backend). Details: [phase4a_robustness.md](phase4a_robustness.md),
[phase4b_latent_regime.md](phase4b_latent_regime.md),
[phase4c_transformer.md](phase4c_transformer.md). Test suite: 384 tests pass.

| # | question | answer (measured) |
|---|---|---|
| 1 | How often does sparse top-2 fail to converge? | **0 of 30** pre-registered validation failures on the Phase 3 task (exact 95 % CI 0–11.6 %), same as dense (0/30); top-1 straight-through 1/30 (CI 0.1–17 %). The Phase 3 failures were an artefact of a non-reproducible initialisation draw; the only failed run was slow symmetry breaking after an initial expert collision (27/30 seeds start with a collision; dense and top-2 resolved all of them). In the latent-regime task no run stalled in any condition; the oracle-relative threshold flagged near-floor runs in `easy` only. |
| 2 | Does the balance loss improve stability? | **No.** For top-2 it is neutral (0/30 → 0/30 failures, mean test MSE +5e-6, slightly tighter spread, utilisation 0.44–0.56 → 0.46–0.54). For top-1 it is harmful: every run acquires misrouted test tokens (median test MSE 5e-13 → 4.1e-3) and one run drifts upward late in training. Coefficient 0.01 chosen on disjoint validation seeds. |
| 3 | Does sparse routing work without explicit regime indicators? | **Yes.** With Gaussian-mixture inputs the router's regime purity equals the Bayes-optimal identification accuracy in every condition (0.99 / 0.81 / 0.52 vs 0.994 / 0.825 / 0.549) and each expert takes one regime; dense, top-2 and top-1 all specialise. |
| 4 | How does performance change as regimes overlap? | Easy (Δ = 5.66): dense ≈ top-2 (9.4e-3 vs 9.8e-3; dense marginally better, 3/10 seeds for top-2); medium (Δ = 2.83): tie (0.162 vs 0.157, CI spans zero, one dense seed left two regimes on one expert); hard (Δ = 1.41): **dense better on 10/10 seeds** (0.318 vs 0.342) because 98.5 % of inputs are ambiguous and the optimal predictor is a soft mixture; hard top-1 is worst everywhere (0.416 in hard). Dense and top-2 both beat the hard-Bayes oracle in medium and hard by mixing; single adapters stay at 0.39–0.46 regardless of overlap. |
| 5 | Does sparse MoLoRA improve transformer adaptation quality? | Dense MoLoRA and sparse top-2 are **tied** (test CE 2.2546 vs 2.2549, paired Δ +0.0003 [−0.0024, +0.0029]) and both beat the parameter-matched LoRA r=18 by 0.013 nats on 5/5 seeds (CI [0.012, 0.015]); LoRA r=4 is 0.085 worse; top-1 is 0.040 worse. Adapters close ≈ 80 % of the frozen-to-oracle gap. The routing benefit exists but is small at this scale. |
| 6 | Does sparse execution reduce end-to-end transformer runtime? | **No.** Training step: sparse k=1 0.80–1.09× dense, k=2 0.98–1.35×, k=4 1.19–1.69×; inference forward 1.0–1.4× dense. Adapter layers are 42–57 % of the forward, but inside them gather/scatter + router (1.6–4.3 ms) outweigh the expert matmuls saved (0.3–1.3 ms). Expert FLOPs are exactly k/E of dense in every run. |
| 7 | Does sparse routing reduce peak training memory? | **Yes**, consistently: per-step peak Python/NumPy allocation is 67–69 % (k=1) and 79–83 % (k=2) of dense in the transformer, 40 % / 64 % in the single-layer benchmark, and 62 % for E=8, k=2 vs dense E=8. This is activation/gradient memory, not parameter memory (identical for dense and sparse). |
| 8 | Which results are robust across seeds? | Dense and top-2 never failing (30 + 30 runs); top-2 < dense on the one-hot task (29/30 paired seeds, CI away from zero); dense < top-2 in the hard latent condition (10/10); top-1's bimodality and brittleness (30 + 30 runs); dense = top-2 in the transformer (5/5 within noise) and both > matched LoRA (5/5); memory savings in every configuration. |
| 9 | Which conclusions remain limited to synthetic settings? | All of them: single-layer regressions with planted low-rank corrections, isotropic Gaussian regimes with orthogonal means, a 16-token Markov task, a 71 k-parameter transformer, 5–30 seeds, one initialisation policy, no real text, no GPU. Effect sizes in the transformer are ~0.01 nats and should not be extrapolated. |
| 10 | Is further systems optimisation justified? | Only if CPU latency of this Needle implementation matters: the dispatch cost is Python-level op overhead and NumPy gather/scatter, so a fused per-expert kernel or a batched expert matmul could move the break-even, and the memory saving is real. For the research question — whether routing helps — the bottleneck is scientific (task realism, scale), not systems. |

Not done in Phase 4: QLoRA / quantised backbone (not implemented, not tested,
not claimed); q/v-projection adapters were implemented and tested but not
evaluated; no real-text corpus.
